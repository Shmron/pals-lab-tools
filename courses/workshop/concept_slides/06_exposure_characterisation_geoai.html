Concept: from daily rows to one number per trimester

Notebook 04 gave us ~17,000 participant-day rows. Notebook 05 gave us ~567,000 grid-cell-day rows. Joining them by (grid_id, date) gives every participant-day an environmental value — then we collapse that down to something a person can reason about: one row per participant per trimester.

17,000 participant-days ⋈ 567,000 grid-cell-days (join on grid_id + date) │ ▼ participant-day-environment table (still ~17,000 rows, now with temp/PM2.5/NDVI attached) │ groupby(PID, trimester).mean() ▼ participant_summary (60 participants × 3 trimesters = 180 summary rows)
Why migrants matter here: a migrant's trimester 1 and trimester 3 locations have different climate baselines — so the migrant/non-migrant exposure-delta comparison (Exercise 2) is the moment Notebook 04's work pays off numerically, not just conceptually.

Concept: GeoAI — natural language to SQL, safely

The GeoAI box sends your question to an LLM (Claude Haiku) running on the PRECISE server, which returns one SQL SELECT statement — shown to you before it runs.

"how many participants have PM2.5 above WHO guideline?" │ ▼ (model receives only table/column names — never the data itself) SELECT COUNT(*) FROM participant_summary WHERE pm25_mean_t1 > 15 │ ▼ validated: only SELECT allowed — INSERT/UPDATE/DROP are blocked ▼ shown to you → you check it matches your intent → then it runs
The one rule that matters most in this whole module: always read the generated SQL before trusting the result. AI-generated SQL can misinterpret a question — the safeguard is a human checking it, not the model being infallible.
